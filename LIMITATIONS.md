# Known limitations, in full

This is the full text of every limitation the README lists in short form: the same
titles, the same three classes with the same counts, ordered here by who hits each one
first. Each entry states its claim, then what to do, then folds the history and the
measurements behind it. Nothing was cut when the README's section became short; it was
folded. The titles are the keys the test suite's hole ledger and the maintainer's release
gates read, so a title here is a hole the suite asserts or names as unassertable.

**The guarantee does not live in your Claude Code session.** It used to be four hooks running inside your Claude Code session, deciding what a command would do by reading the command's text. As of 2026-08-04 that layer is advisory **in mechanism as well as in name**, and since 2.8.0 it is smaller: the two gates that read commands to warn are gone, the scope hook reports what it would have decided about a write, why, and the code, and then lets the write proceed, and the bypass deny's one refusal is a nudge that stops an obvious spelling of disarming the git hooks. The git hooks below are what refuse the work. This wording used to describe a warning while the gates actually denied, and the gap cost a release cycle: successive rounds of adversarial review found that most new defects sat in parser code written that same day to fix the previous round's findings, and while the parsers could deny, every one of those defects was release-blocking. **The trade is explicit.** A false positive is now noise instead of a blocked command. Since 2.9.0 the scope hook's reason **reaches the agent's context** (it rides `additionalContext`, the field Claude Code delivers to the model, and since 2.11.0 it answers no permission prompt), and there it persuades and does not refuse: an agent that receives it may judge the write harmless and proceed. **Advisories persuade; hooks refuse.** The in-session feedback that holds is the **git hooks' refusal messages**, arriving as ordinary command output at the moment of the attempt, which is where the guarantee lives anyway. Through 2.8.0 the reason did not reach the agent at all; that history, and how it was measured, is under Design boundaries below. The guarantee moved to **git hooks**, stamped into a tracked `.githooks/` directory, which git runs itself after it has already parsed the arguments and resolved the refs. For cooperating use there is nothing left to spell around at that point: a merge is a merge however it was written. That is a claim about the SHELL, which it survives, and not about a committer crafting merge topology to evade the audit, which it does not. **Within the git-hook layer, the guarantee is the push-time trunk audit specifically.** The two per-merge hooks keep refusing at commit and merge time, and that early refusal is the feedback you feel day to day; the audit at `pre-push` is what stands between unreviewed work and a shared trunk, and it decides by identity and ancestry (does this history descend from the instance's declared baseline, the commit the upgrade records when it delivers the git hooks, or the commit that stamped the instance when the two arrived together; did this content arrive through a closed spec's lineage) rather than by recognising the shape of any operation. A route past a per-merge hook is therefore a MAJOR in this project's severity model, not a release blocker: the work is refused later than intended, at push, rather than not at all.

Why the change: across five releases, every hardening pass closed one spelling and the next release found another, because a shell command can compute its own arguments and the set of spellings has no end. Then the parser layer died on macOS for a reason that had nothing to do with command text, silently allowing everything, while a git hook on the same machine in the same run was untouched. A parser has failure modes its subject matter does not.

Both halves of the boundary are worth stating plainly, because an enforcement layer whose edges you cannot see is one you cannot reason about.

**The threat model, in three sentences.** A git hook can refuse what git hands it after the shell is done: a commit, a merge or a push whose history skipped the process, judged by identity and ancestry rather than by how the command was spelled. It cannot refuse what never reaches it: a flag or variable that skips it (the escapes below), a clone that never armed it, a checkout that removes it, content the forge does not expose to the check, or a committer who crafts history to pass the audit, which is why every surviving bullet below is stated as a fact about git, the forge or the harness rather than as a defect waiting for a fix. And every release's own adversarial review drives the shipped bytes with those routes as its brief: a route it finds is fixed before the release ships, or it is the boundary of a capability and is named here, because a release never grows this list for any other reason.

The list below is not one kind of thing, which is why it arrives in three groups rather than as one wall. **Design boundaries** are decisions with a date and a reason, where the layer deliberately stops. **Open limitations** are real defects or gaps with a fix scheduled, a candidate, or a named gate, each carrying its status. **Upstream conditions** are things this project does not control, with what would lift them and how that is re-checked every release. A design boundary read as a defect overstates the problem; a defect read as a decision understates it. **The counts live on the group headings below and nowhere else**, so there is exactly one place for them to be wrong and it is the place that moves when a bullet does.

### Design boundaries (24)

These are boundaries, not bugs. Setlist governs the session; it is not a server-side policy engine and does not try to be one. Each one is a decision, and each says when it was taken and why.

#### Week one, one developer

<a id="per-clone-hooks"></a>
- **Git hooks are per-clone, and the tracked directory narrows that without closing it.** `.git/hooks` is not cloned, which is exactly why the hooks are stamped into a tracked `.githooks/` instead: they are versioned, reviewed in diffs, and present in every clone.
  **What to do:** Run `/setlist:upgrade` (or `scripts/refresh-instance.sh --apply .`) in every clone; for a team, require the forge check on the trunk.

<details><summary>The history and the measurements</summary>

What is still per-clone is the CONFIG pointing at them, since `.git/config` is not cloned either, so a fresh clone is unprotected until it is set up. The same applies to `merge.ff=false`, which Setlist sets because a fast-forward merge fires no git hook at all. Expect merges that used to fast-forward to create merge commits; that is the setting doing its job. For a team, the stamped forge check (2.6.0) is the layer that does not live in a clone: required on the trunk, it verifies every pull request against the same predicates whether or not the committer's clone had its hooks armed. It is a boundary only where it is required, and the check says so when it is not.

</details>

<a id="no-verify"></a>
<a id="skip-hooks-escape"></a>
- **`--no-verify` and `SETLIST_SKIP_HOOKS=1` skip the git hooks, the push-time audit included.** `--no-verify` skips git hooks, and `git push --no-verify` skips the pre-push audit. Setlist's own escape hatch is read FIRST by every stamped git hook, `pre-push` included since 2.2.0, and at push it skips the trunk audit and the content scan both, saying so on stderr; `SETLIST_SKIP_TRUNK_AUDIT=1` is the narrow escape, skipping the audit alone while the content scan still runs.
  **What to do:** Treat both as the escapes they are: reach for `SETLIST_SKIP_TRUNK_AUDIT=1` when you mean to skip the audit alone, never carry the wide variable in a shell profile, and put the forge check on the trunk if the trunk must hold against either.

<details><summary>The history and the measurements</summary>

This is a real hole and a different kind of hole from the others: a deliberate act with an obvious name, not an apostrophe in a commit message. Setlist's own escape hatch, `SETLIST_SKIP_HOOKS=1`, is the same thing said out loud. Since 2.6.0 the refusal text no longer names the escape; the escape is documented here and in the hooks' own headers, and the forge check has no escape variable at all: a workflow edit is a reviewed change under the stamped CODEOWNERS.

**Until 2.11.0 this bullet was titled "`--no-verify` skips git hooks", and the escape variable was a bullet of its own, "The `SETLIST_SKIP_HOOKS=1` escape skips EVERY git hook, `pre-push`'s trunk audit and content scan included.", merged here in 2.11.0** because the two are one boundary: a deliberate act with an obvious name that a git hook cannot refuse, answered by the forge check, which reads neither. That bullet's own advice stands: Reach for the narrow variable when you mean to skip the audit alone, and never carry the wide one in a shell profile. Its history follows.

**This bullet said the opposite from 2.1.0 through 2.4.1** ("not read by `pre-push`", so a refused push would not get through), which was true when it was written and false from the 2.2.0 hook onward, in the unsafe direction: a reader carrying the variable for a noisy commit hook was told it was inert at push and it was not. Corrected in 2.5.0 by that release's adversarial review, with the suite case behind it rewritten to pin the escape in its real direction (it had reported a pass either way). A deliberate act with an obvious name, like `--no-verify` above. Since 2.6.0 the refusal text no longer names the escape; the escape is documented here and in the hooks' own headers.

**A third route to the same effect, measured by the 2.8.0 adversarial review.** `pre-push` finds the trunk audit through `CLAUDE_PLUGIN_ROOT` before the instance's own stamped copy and does not check what it found, so a shell that sets that variable to a directory holding its own `scripts/trunk-audit.sh` runs that script instead, and a push of unclosed work can then succeed with nothing printed. The variable is not set in an ordinary Claude Code session's shell (Claude Code sets it for plugin hook and skill processes, pointing at the real plugin), so meeting this takes a deliberately planted directory, and the bypass deny does not recognise it.

</details>

<a id="hookspath-conflict"></a>
- **git allows one `core.hooksPath`, so Setlist runs another hook manager's hooks through its own rather than beside them.** Where husky, lefthook or pre-commit already runs, the stamp and `refresh-instance.sh --apply` arm `.githooks/` and CHAIN the other layer: its location is recorded as `hooks_chain` in `.claude/sdd.json`, every Setlist git hook runs that layer's hook of the same name (in `pre-commit` and `pre-merge-commit` before its own checks, so a hook that restages, as lint-staged does, changes what Setlist's scan reads rather than what it already read; in the rest after its own verdict), and a fixed pass-through is written under each other hook name it carries (`commit-msg`, most often), so both refusals surface. It stays one directory, git's rule: a manager that puts `core.hooksPath` back on install (husky's `prepare` script does, on `npm install`) switches Setlist off again, which the next session start reports as `[SR-HOOKS-NOT-ARMED]`; a clone where the manager was never installed runs Setlist's hooks and reports the chained layer as missing, and a record the hooks cannot read (jq absent, a file that does not parse) or a chained directory that runs a Setlist hook again is reported the same way; and a layer the refresh cannot see (a configured directory that is absent or unreadable) is still refused rather than chained, as is a `.githooks/` that already holds a hook that is not Setlist's, which arming would switch on.
  **What to do:** Commit `.claude/sdd.json` and the `.githooks/` pass-throughs with the migration. When a session opens with `[SR-HOOKS-NOT-ARMED]` after a dependency install, run `/setlist:upgrade` (or `scripts/refresh-instance.sh --apply .`), which chains the manager again. `SETLIST_ADOPT_HOOKSPATH=1` displaces the other layer instead, chaining nothing.

<details><summary>The history and the measurements</summary>

Measured: the identical `git commit` was refused by `.husky/pre-commit` before the refresh and committed cleanly after it. What gets displaced is often itself a control, since gitleaks, detect-secrets and commit-msg validation are commonly wired exactly this way. Report mode now names the value it would displace and what stops running; `--apply` refuses and tells you the two ways forward, which are to move those checks into `.githooks/` or to re-run with `SETLIST_ADOPT_HOOKSPATH=1` and displace the other layer on purpose. Through 2.10.0 this read: "This is a limitation of git rather than of Setlist: the two layers genuinely cannot both run, and the only thing that was ever fixable is whether you find out."

**Until 2.11.0 the title read "git allows one `core.hooksPath`, so Setlist cannot coexist with husky, lefthook or pre-commit, and `refresh-instance.sh --apply` now REFUSES rather than displace one silently."** In 2.11.0 the refusal became a chain (spec 0173), because git's one-directory rule decides where git LOOKS, not what may run from there: every Setlist git hook runs the displaced manager's hook of the same name with the same arguments (the same ref lines on `pre-push`, and none on a push that updates nothing), at its exit, or in `pre-commit` and `pre-merge-commit` before its own checks, and the status carries both verdicts. Measured red and green on husky 9's and lefthook's layouts: before, the stamp refused, and under `SETLIST_ADOPT_HOOKSPATH=1` both managers' `pre-commit` and `commit-msg` stopped running; after, the manager's `pre-commit` refusal refuses the commit with `[SLH-CHAIN-REFUSED]`, its `commit-msg` rejects a non-conventional message through the pass-through, and a commit both layers refuse prints both. Measured against the real husky 9.1.7 installed from npm: `husky init` sets `core.hooksPath=.husky/_`; the stamp chains it; and `npm install` runs husky's `prepare` script, which sets `core.hooksPath=.husky/_` again, after which only husky runs and the next session start reports it. The narrowed title is that fact: one directory, which Setlist now shares rather than takes.

</details>

<a id="fast-forward"></a>
- **`git merge --ff-only`, `--ff` and `--squash`: a fast-forward fires no merge hook, and squash needs one flag under the stamped setting.** A fast-forward creates no merge commit, so there is no `pre-merge-commit` for git to run, and an explicit `--ff-only` beats the `merge.ff=false` Setlist sets; that same setting implies `--no-ff`, so git refuses a plain `--squash` with `fatal: options '--squash' and '--no-ff.' cannot be used together`, on every squash merge, whether or not the branch could have fast-forwarded.
  **What to do:** Close with `--no-ff` (what `/setlist:checkpoint` does); for a one-off squash use `git -c merge.ff=true merge --squash <branch>`; if a GUI passes `--ff` for you, expect the audit at push to be the layer that speaks.

<details><summary>The history and the measurements</summary>

So does a bare `--ff`. Unlike `--no-verify` neither looks like a bypass, which is why they are called out here: they are normal preference flags and some GUI clients pass them for you. What this costs you is the merge-time close verification, which does not run: the commit-time checks and the push-time trunk audit both still do, and the audit reads the close conditions off the commit itself, so a COMPLIANT fast-forward close is accepted at push WHEN THE CLOSE ARRIVES AS ONE COMMIT: a fast-forward of a single-commit branch, or a `--squash`. A fast-forward of a MULTI-commit branch lands the branch's earlier commits on the trunk as ordinary single-parent commits the audit reads one by one, so the intermediate work commits are refused as feature code with no close (measured by the 2.4.0 review; the close exemption covers the closing commit, not a range). `--no-ff` remains the recommended way to close, and is what `/setlist:checkpoint` does, because it is the only route that runs every layer. The suite is separately not re-run by the audit. **Fixed as of 2.4.0 for a close that arrives as ONE commit, and a decided boundary for what remains (ruled 2026-09-02, when this bullet moved here from Open limitations): git fires no hook for a fast-forward, `merge.ff=false` is the stamped answer and `--no-ff` the recommended close, and a multi-commit fast-forward refusing at push on its intermediate commits is the audit doing its job.** A compliant `--squash` close, or a fast-forward of a single-commit branch, is no longer refused at push; the two layers agree there, and the audit decides on the parent COUNT so one rule covers both flag names. A multi-commit fast-forward still refuses on the branch's intermediate commits, as the bullet now states (recorded by the 2.4.0 review, which is also what corrected this bullet's Status from claiming the fix whole).

**The squash half, a bullet of its own from 2.4.0 to 2.9.0 ("`git merge --squash` needs one flag to work in a Setlist instance, and the error does not say so."), merged here in 2.10.0** because both are one setting, one boundary and one consequence, fixed jointly. The message names neither Setlist nor the setting, so there is nothing to search for. Use `git -c merge.ff=true merge --squash <branch>` for a one-off, or drop the setting for that command. A squash has no second parent, so the trunk audit can never see the branch the work came from; it reads the close conditions off the commit instead, so a COMPLIANT squash close is accepted at push. As with a fast-forward, what you lose is the merge-time close verification, and `--no-ff` stays the recommended close because it runs every layer. The setting stays because a plain fast-forward merge fires no git hook at all, and that hole is worth more than the convenience. **Fixed as of 2.4.0, jointly with the fast-forward half above, for a close that arrives as ONE commit, and a decided boundary for what remains (ruled 2026-09-02, when this bullet moved here from Open limitations): git's own error message names neither Setlist nor the setting, and the setting stays.** A compliant `--squash` close is accepted at push; the two layers agree there, and the one-off flag above remains the way to run a squash. (This bullet's Status read "fix scheduled for the next release cycle" for one release after the fix shipped, and was corrected 2026-09-02 by the release's own claims-vs-bytes review rather than by a reader.)

</details>

<a id="trunk-name"></a>
- **The trunk audit's frame is declared in `.claude/sdd.json`, the trunk by name and the baseline by commit, and a declaration is a claim under the same custody as the rest of `.claude/`.** Every git hook asks "is the checked-out branch the recorded trunk" by comparing names, so an instance that merges onto a differently-named branch is ungoverned; and the audit walks the history that descends from `audit.baseline`, the commit the upgrade records when it delivers the git hooks to an instance whose history predates them, or, with no key, the commit that introduced `.claude/sdd.json`.
  **What to do:** Record in `.claude/sdd.json` the branch you actually merge onto, leave `audit.baseline` as the upgrade wrote it, and review a change to either as you would a change to the hooks.

<details><summary>The history and the measurements</summary>

On a git-flow shaped repository, where the team works on `trunk` or `develop` which tracks `origin/main` while a local `main` also exists as the release branch, a recorded trunk of `main` means every hook takes its fail-open exit while merges really do advance the branch the project treats as its trunk. Measured on the shipped bytes: unspecced role-path code lands on that branch with the whole guarantee layer silent. Between 2026-08-05 and 2026-08-07 the hooks also consulted what the branch TRACKS, which closed this shape and broke a much commoner one: `git checkout -b <name> origin/main` is git's own documented way to branch from a remote trunk, git announces it with "set up to track", and every such branch became the trunk to the hooks, so merging role-path code into an ordinary spec or feature branch was hard-refused with a message naming `main` as the target of a merge that never touched it. The two shapes are indistinguishable from inside a hook, so the tracking test was removed and this limitation is the honest statement of what is left. **The remedy is one line**: record in `.claude/sdd.json` the branch you actually merge onto. The upgrade skill prescribes exactly that.

**The baseline half arrived in 2.10.0, and this bullet, which named the trunk alone through 2.9.0 ("The trunk is recognised by the NAME recorded in `.claude/sdd.json`, so an instance that merges onto a differently-named branch is ungoverned."), was rewritten to carry both.** An instance stamped before its git hooks existed and upgraded across them was refused on every push, for merges made before any hook could have witnessed them, because the audit's walk began at the commit that introduced `.claude/sdd.json`. The refresh now records `audit.baseline` in the migration commit (the commit that added `.githooks/pre-push`, or the trunk's tip when it delivers the hooks now) and never overwrites a key already there; where the recorded trunk is not a branch in that clone it records NOTHING and names the branch it looked for, because a key the audit cannot use is worse than no key. The audit refuses a key that is not a full commit id, the absent key and a present non-string included (`SLH-BASELINE-MALFORMED`), that does not resolve in the repository (`SLH-BASELINE-UNRESOLVED`), or that is not an ancestor of the tip being audited at all (`SLH-BASELINE-NOT-ANCESTOR`), each before anything is walked, and its report says whether the frame was `(declared)` or `(default)`. A key that is an ancestor but sits off the trunk's first-parent line, which is the commit the refresh records when the hooks arrived through a merged branch, is not refused: the frame is computed rather than required, and the walk starts at the oldest commit on the tip's first-parent line that contains the declared commit (the commit itself, or the merge that brought it in), the report names both when they differ, and the refresh and `/setlist:validate` read the key through the same function the audit runs. A key moved forward to the tip walks nothing and reports clean: that is a declaration the reviewer of `.claude/` signed, disclosed here rather than refused. The forge check passes its own `--since`, the pull request's base, and under `--since` the key is not read at all, so a pull request that moves the key in its own checkout does not move the forge's frame.

</details>

#### Ordinary use

<a id="empty-remote"></a>
- **A first push to a brand-new EMPTY remote audits every pushed branch as a trunk candidate.** An empty remote has no default branch yet, and git hosts adopt the first pushed branch as the default, so `pre-push` cannot know which pushed ref is about to become the trunk and audits them all.
  **What to do:** Push the trunk first, alone; use `SETLIST_SKIP_TRUNK_AUDIT=1` only for a deliberate exception.

<details><summary>The history and the measurements</summary>

The clean trunk pushed on its own passes; a spec branch pushed first, or alongside the trunk, is audited as if it were the trunk and refused, because unclosed feature code must not become a remote's default by a raw push. Push the trunk first, or use `SETLIST_SKIP_TRUNK_AUDIT=1` for a deliberate exception. This is FAIL-CLOSED: it refuses more than you might expect, and it closed a fail-open that adversarial review found, where a differently-named branch pushed first to an empty remote was ALLOWED while the hook audited a local ref the push never touched.

</details>

<a id="review-ref-namespace"></a>
- **The push-time hooks read only the branch and tag namespaces, so a push to a review-ref namespace is ungoverned by them.** `pre-push` runs the content scan and the trunk audit over `refs/heads/*` and `refs/tags/*`; a push to any other namespace, of which Gerrit's `refs/for/<branch>` is the common one, matches neither and both checks are skipped.
  **What to do:** Push the trunk directly so the audit reads it, or require the stamped forge check on the trunk; since 2.7.0 the hook REPORTS the skip by name rather than passing in silence.

<details><summary>The history and the measurements</summary>

Found by the 2.7.0 adversarial review, which measured a live-shaped secret reaching the remote at exit 0 by this route. **What changed in 2.7.0 is the silence, not the scope:** `pre-push` now emits `SLH-REF-NOT-AUDITED` naming the ref and both ways through, and it refuses nothing, so no ordinary push is denied by it. **The scope was deliberately NOT widened**, and the reason is this project's own history rather than indifference: teaching the hook another forge's ref grammar means shipping a spelling nobody here can exercise end to end, and an unexercised spelling is the class that produced the two defences removed on 2026-08-07 for refusing ordinary work. Native support for review-ref workflows waits on a field report from someone who runs one, which is the same trigger the forge-check work carried. On such a workflow the forge check is the layer that holds, because it judges the merge a change request would make rather than the ref that carried it.

</details>

<a id="scan-scoping"></a>
- **The staged-content scans read every staged line unless you scope them.** By default the em-dash and secret scans do not know vendored third-party code, quoted external text, or test fixtures with dummy credentials from your own new writing, and **splitting the commit does not help, which this list said it did until 2026-08-04**: the scans read every added line of the index, so isolating the foreign content isolates it WITH the scanner rather than away from it.
  **What to do:** Declare repo-relative globs in `scan_exclusions`; every skip is printed with the glob that matched it.

<details><summary>The history and the measurements</summary>

Since 2.2.0 you scope them by declaring the paths, repo-relative globs, in `.claude/sdd.json`: `"scan_exclusions": ["vendor/**", "test/fixtures/**"]`, honoured by both scans at the commit layer and the push layer alike. **Every skip is printed, naming the file and the glob that matched it**, because an exclusion nobody is told about is a hole one directory over. The deliberate limits, which are the reason this is scoping and not an off switch: the set reaches the two content scans and nothing else, so it cannot quiet the trunk audit, the close checks or role-path judgment; a pattern made only of wildcards is refused, which stops the obvious off switch but is NOT the same as "no spelling reaches everything": the guard strips `*`, `?` and `/` and asks whether anything is left, so `*.*` leaves a dot, passes, and excludes every path with an extension. That was measured in 2.7.0 and the sentence here claimed the stronger property until then. Read the guard as refusing the bare catch-all, and read the exclusion set as a declaration you are responsible for; an unreadable set is refused with a named code rather than resolved in either direction; matching is case-exact and a path git had to quote is scanned and says so, because failing to exclude costs a refusal you can see while failing to scan costs a published secret. Declaring nothing leaves the scans exactly as they were. **The one residue left in 2.8.0:** through 2.7.0 the in-session advisory commit gate did not read exclusions and its message said so, naming the git-hook layer as where they are evaluated; that gate is gone, so a commit of excluded content draws nothing in a Claude Code session and commits cleanly through the hooks. Do not edit third-party content to satisfy a style gate. **Built in 2.2.0 for the layer that carries the guarantee, and a decided boundary for the advisory half (ruled 2026-08-28; moved here from Open limitations 2026-09-02): the session gate is not path-scoped, the divergence is closed by honesty rather than by coupling, and the message that says so shipped in 2.3.0.** (This bullet's Status called the advisory half "the remaining piece" for two releases after that ruling; corrected 2026-09-02.)

</details>

<a id="scan-best-effort"></a>
- **Secret and style scanning is best-effort early warning, not a guarantee.** Treat any secret that reached a commit as COMPROMISED and rotate it, whatever these hooks reported.
  **What to do:** Treat any secret that reached a commit as COMPROMISED and rotate it, whatever the hooks reported; send pattern misses as field reports.

<details><summary>The history and the measurements</summary>

This limitation is written at this strength because the claim above it was narrowed three times and falsified three times under the 1.1.0 adversarial review (2026-08-06), and the mechanism is what decides which sentence is true. **Two structural holes remain, and they are structural rather than a matter of pattern coverage.** The scanner reads the output of `git diff`, which is a RENDERING the repository controls: a `.gitattributes` entry marking a path `-diff` or `binary` made git emit no added lines at all, and a live-shaped secret then reached a remote at exit 0 by the ORDINARY commit-and-push path (measured under adversarial review; narrowed in 2.11.0, below); and the repository's own diff CONFIGURATION shapes the same rendering, which is the structural class the `.gitattributes` case belongs to: colour forced into a pipe, an external or textconv driver, a driver whose hunk-header regex does not compile, the setting that renders a root commit as nothing, each found by measurement and each closed as of 2.4.1 by flags that ignore configuration and by reading git's own exit status, while the class itself stays open because a rendering has no last setting. And the pattern set is a first cut rather than a complete secret detector: it matches token-shaped and connection-string-shaped values, so it will miss exotic formats and can flag something innocent; tuning comes from field reports, so send them, and there is no scheduled cycle for it because the tuning that would help is the tuning real misses tell us about (that sentence was a bullet of its own until 2026-09-02, merged here because the list said it twice). Separately and not a hole in the scan: git fires no hook for `cherry-pick`, for `rebase`'s intermediate commits, or for the apply step of `git am`, so those are read at push rather than at commit. What the scan is good for is catching an accident early on the ordinary path. It is not a control you can put between a secret and a remote. **The four holes once scheduled here were FIXED in 2.2.0** (the endpoint diff became a per-commit walk of the pushed range, the first-push range derives against the remote's own refs instead of coming out empty, a tag push is scanned for what it publishes, and the `+++` header strip is anchored to the header), **and what remains is structural and stays by decision (2.2.0, restated 2026-09-02 when this bullet moved here from Open limitations)**: the rendering, which a `.gitattributes` entry can suppress and configuration can reshape, and the pattern set; the hookless routes named above are git's and not the scan's. The sentence at the head of this bullet is the one to trust either way.

**The attribute hole, narrowed in 2.11.0 (spec 0173).** A path the plain rendering reports as binary is re-rendered with `git diff --text` and scanned when its new content passes git's own text test (no NUL byte in its first 8,000 bytes), at commit, at merge and for every pushed commit with one parent: a `-diff` or `binary` entry no longer hides a text file, and a real binary is still not read (a blanket `--text` would have read this project's own demo GIF, which carries the em-dash's three bytes, as an em-dash). Measured red and green: a live-shaped secret in a path marked `-diff` or `binary` reached the remote at exit 0 and is refused at commit and at push. What stays: a MERGE commit's own change to such a path is not read at push, because git's combined diff prints "Binary files differ" under `--text` as well (git 2.55.0, measured); `pre-merge-commit` reads it when the merge is made with the hooks armed.

**What the scans read, a bullet of its own through 2.9.0 ("The scans read this project's own index."), merged here in 2.10.0.** `pre-commit` reads the index git is committing, in the project it governs, so a commit aimed at another repository is not a hole in these bytes but a property of git; give a nested repository its own instance if it should be governed. A commit aimed at another repository is therefore not scanned: `git -C some/nested/repo commit ...` commits that repository's index and runs that repository's hooks, not this project's. A commit made in this project through `GIT_INDEX_FILE=...` IS scanned, because the hook reads whatever index git is committing; through 2.7.0 this bullet called that a second hole, which was the retired commit gate's alone, measured for 2.8.0 on an instance armed with the stamped hooks and pinned by the suite. Your own staged content is checked, every time. A nested repository is a different project, and if it should be governed it should have its own instance.

</details>

<a id="checkout-switch"></a>
- **A checkout decides which hooks exist: a branch that does not carry `.githooks/` runs no git hook, and commit and merge time read the checked-out `.claude/sdd.json`.** git runs the hooks the checked-out tree carries, so an ordinary checkout of a branch that never carried Setlist removes `.githooks/` and git runs no hook at all, `pre-push` included; `pre-commit` and `pre-merge-commit` open by checking that the CHECKED-OUT branch carries `.claude/sdd.json` and exit silently when it does not. `pre-push` reads the pushed commits: from a checkout that still has its hooks but no `sdd.json`, a push whose tip carries one is governed by that commit's own configuration, the trunk audit reading each pushed trunk tip's own, and a trunk tip that carries none is reported unaudited (`SLH-REF-NOT-AUDITED`) rather than read under another tip's.
  **What to do:** Keep `.claude/sdd.json` and `.githooks/` on every branch that carries governed work, and require the forge check on the trunk, which reads the branch a pull request carries rather than what is checked out.

<details><summary>The history and the measurements</summary>

That guard is deliberate and load-bearing, because a `core.hooksPath` set in one repository must not govern unrelated work. The consequence is that the guard is also a switch: measured on the shipped bytes, a push of an unclosed merge is refused from the trunk and the IDENTICAL push of the IDENTICAL commits succeeds after checking out an orphan or legacy branch that has no `sdd.json`, and the work reaches the remote trunk (measured under adversarial review). If your repository carries branches without the file, the enforcement boundary is conditional on which branch happens to be checked out. Through 2.10.0 this was documented rather than closed: narrowing the claim was the recorded decision once repeated repair rounds kept introducing new defects, and a fix here would have to distinguish "not a Setlist project" from "a Setlist project standing on an unstamped branch", which the file alone cannot do. The forge check closes this at the one layer where a branch is read rather than checked out: a pull request whose head carries no `.claude/sdd.json` is refused, not waved through.

**Until 2.11.0 the title read "A checkout is an enforcement switch: every git hook is inert on a branch without `.claude/sdd.json`."** and every hook opened with that check, `pre-push` included. In 2.11.0 `pre-push` reads its ref lines first and asks whether the work being PUSHED is governed, which is a fact about the pushed commits rather than the checkout: governed when the checkout carries the file, as before, or when a pushed tip does, and then the trunk audit reads each audited tip's own configuration and the push's other readers the first governed tip's (until this release's adversarial review one tip's configuration served every ref, so a sibling branch listed first audited the trunk under its looser roles), and a trunk tip that carries none is reported unaudited by name; a push whose tips carry no `sdd.json` from a checkout without one stays ungoverned, which is the guard's purpose. Measured red and green: the same unclosed merge pushed after `git checkout --orphan` (the working tree, hooks included, kept) was accepted and is refused by the audit. What it cannot reach is measured too: a branch that never carried Setlist has no `.githooks/`, an ordinary checkout of it leaves git no `pre-push` to run, and the identical push succeeds, which is why the title narrowed rather than retired. `pre-commit` and `pre-merge-commit` keep the checked-out reading.

</details>

#### Diagrams as claims (2.7.0)

<a id="diagram-checks"></a>
<a id="path-shaped-names"></a>
<a id="render-check"></a>
- **A diagram check compares a claim to a diff and a lockfile to a command's output; it does not judge whether a drawing is true of the code.** The field checks establish that the files the closer named are the files the commit touched, the node check that every drawn path exists in the tree, and the lockfile that the generated view equals what the declared command prints. A drawn name is verified only when it is path-shaped, and everything else is reported rather than checked: a name counts as a path when it contains a slash and no whitespace, so `api["src/api"]` is resolved against the tree and `api["The API"]` is not. And the render check runs where a renderer runs: inside `setlist-forge-check.yml` the parser step succeeds or fails the job; the stamped script run anywhere else reports that it could not parse and refuses nothing on that ground; local git hooks never render.
  **What to do:** Review a diagram the way you review a Closing report, and run the baseline chore under your own eyes. Write a path in the node's own label, not only in the node id, and read the printed skip list; require the check on the trunk, and on a forge that is not GitHub put a Mermaid parser on the runner's PATH.

<details><summary>The history and the measurements</summary>

That a box, an arrow or a label is TRUE of the mechanism is what review establishes, and `chore/diagram-baseline`'s file-by-file human review is the first instance of it: the one legitimate scan in the framework is the one a person signs. Three verdicts, by whose node it is: a stale node the CLOSING spec drew refuses (`SLH-DIAGRAM-STALE-NODE`), an earlier spec's stale node is REPORTED with two honest exits and refuses nothing, and a name that is not path-shaped is printed rather than checked (below). The twelve-node bound is reported at validate and refuses nothing, as are validate's other three diagram reports. The whole half is OPT-IN, and **there are TWO ways to opt in, which is a correction this bullet owes you**: a file under `docs/diagrams/` carrying the four-line header, or a `diagram_command` declared in `.claude/sdd.json`. A project with neither behaves exactly as it did before 2.7.0, which a differential fixture proves rather than assumes. A project that declares `diagram_command` is armed by that declaration ALONE, with no `docs/diagrams/` in the tree at all, because the lockfile arm is the half it opted into. **What arms the checks is what the diagram half itself writes, not the directory**, and that is a correction this release made to itself: until the second 2.7.0 leg the switch was the mere existence of any file under `docs/diagrams/`, a `.png` included, so an upgrade armed the checks for any project that already kept diagrams at that conventional path and started refusing closes it had passed the week before. The switch is now a file under `docs/diagrams/` carrying a `Synced by:` header line, which `chore/diagram-baseline` writes on an upgrade and `/setlist:new` writes on a new project, OR a declared `diagram_command`, because a project whose only diagram surface is a generated view carries no header anywhere and the generated file is the command output rather than a drawing anyone signed. **The residue is worth knowing and is not reported anywhere:** a `docs/diagrams/` tree whose files carry no header does not arm the checks and nothing tells you so, which is the quiet direction rather than the refusing one. If you have drawn diagrams there by hand and want them gate-checked, add the header (cut `chore/diagram-baseline`, or write the four lines) and the checks come on. One consequence of arming them is worth knowing before you do: on an armed instance the OLD field form (`updated in this commit`, naming no files) is refused as a claim that names nothing, because a claim nobody can check is the thing this release exists to remove.

**Until 2.11.0 two bullets of their own stood beside this one, merged here in 2.11.0** because all three say what a diagram check compares and where it runs: "A drawn name is verified only when it is path-shaped, and everything else is reported rather than checked." and "The render check runs where a renderer runs, and the stamped workflow fails its job rather than passing without one.".

**What a drawn name is.** Every unverified name is PRINTED with what it is, a node, a subgraph id or a subgraph title (`SLH-DIAGRAM-NODE-SKIPPED`, up to ten listed with a count beyond that), so the boundary is visible at every close rather than discovered later. What the print cannot do is turn a prose label into a claim: a module identifier with dots and no slash, and a subgraph that draws a process or a trust boundary rather than a directory, have no path to resolve and are checked by nobody. Three Mermaid spellings are not read at all, and they are named here and in the `diagrams` skill so a drawer is told rather than believed: the rhombus and hexagon (`{...}`), the asymmetric (`>...]`), and a label separated from its id by a space (`a ["src/a"]`). The last of those is the price of a strict adjacency test, which was measured and kept because allowing whitespace between an id and its bracket would re-open the false-refusal direction described below. **All three are a design boundary rather than a scheduled fix (2.10.0):** opening them at the layer that carries the guarantee would surface new refusals in live instances, so they stay printed as unread rather than read. **Until 2.10.0 an Open limitation sat beside this bullet**, "Mermaid's inline edge-text form can refuse a close for a path nobody drew.": `a -- reads(src/gone.json) --> b` put its text where a declaration's label goes, so a path inside it was read as a node nobody drew and could refuse the close. It was the narrow remainder of a wider defect found and fixed before 2.7.0 shipped, when the node reader read any bracketed span. Since 2.10.0 the reader treats a span opened by Mermaid's text openers (two dashes, two equals, or a dash and a dot) and closed by a link as an edge label, as the pinned Mermaid parser does, and a declaration beside it is still read; the pipe form, `-->|"text"|`, stays what every type reference teaches.

**Where the render check runs.** A Mermaid block that does not parse is caught at the forge or on the rendered page, never at the commit, because a git hook that needs a toolchain fails for reasons unrelated to the work on a machine whose node nobody chose. The price is a network fetch inside a required check, and it is smaller than this bullet first said it would be: the pinned tool exposes a parse-only entry point, so the step installs `mermaid@11.14.0` and `jsdom` and nothing else. Measured on one host, both paths: parse-only 1.8s and 143MB, a full render 30s and 484MB of packages plus a 493MB browser download, with the two verdicts agreeing on every case of a twelve-case corpus in both directions. So the browser download is not paid. The fetch is also a dependency: a required check that installs a parser from the npm registry can be blocked by a registry outage or by a bad transitive release of a package the pinned version pulls in, and no lockfile is stamped beside the workflow, by decision (2.10.0), because a lockfile removes only the second case and is one more maintained artifact in every instance. The claim the check makes is that the block PARSES under the pinned version, not that a picture was produced. `FC-DIAGRAM-NO-RENDERER` is a report and is reachable only OUTSIDE the stamped workflow, which is what keeps "never a pass on absence" true where the check is required; the step also verifies its own parser in both directions before the check runs, because a parser that accepts a broken block would turn every diagram into a claim nobody checked while reporting that it did.

</details>

#### The session layer: advisory, and its one parser frozen

<a id="hard-deny-expansion"></a>
- **The session layer's one hard deny is defeated by ordinary variable expansion, so read it as a nudge and never as a boundary.** The bypass deny carries the session layer's single hard refusal, `CM-BYPASS-SPELLED`, which exists to stop a command that would disarm the git hooks; `git commit -m ${MSG} --no-verify` is allowed in silence, because an unquoted expansion before the flag defeats the lexer that looks for it.
  **What to do:** Treat the deny as a nudge that catches the obvious spelling, and put the boundary where it holds: the git hooks, and the forge check on a trunk that requires it.

<details><summary>The history and the measurements</summary>

This bullet is written at this strength because the alternative is worse than the hole. The gate's other verdicts have been advisory in mechanism since 2026-08-04; this one deny is the exception, and it is the one a reader is most likely to mistake for a boundary. **What defeats it is not exotic.** `-m ${MSG}` is how a shell script writes a commit message, so a developer meets this while doing nothing unusual, which is why the sentence above does not say "crafted spellings evade it". Crafted spellings evade it too, and they are the same hole rather than a second one: ANSI-C quoting (`git commit $'--no-verify'`), a global option that takes a separate value and shifts where the subcommand is found (`git --attr-source HEAD commit -n`), and `--config-env=core.hooksPath=VAR`, which moves the hooks path without tripping `CM-HOOKSPATH-MOVED`. All four were measured against the shipped bytes by the 2.7.0 adversarial review, each with a replay. The 2.8.0 adversarial review measured more of the same hole on the shipped bytes, each against a repository whose git hooks refuse: the escape variable behind a wrapper other than a bare `env` or `export` (`/usr/bin/env SETLIST_SKIP_HOOKS=1 git commit -m x`, `nice env ...`, `time ...`, `env -i ...`) and a redirection such as `2>&1` placed before the flag (`git commit -m x 2>&1 --no-verify`). A backslash-newline line continuation before `git` or the flag, measured here in 2.8.0, is no longer among them: since 2.10.0 the lexer joins a continued line as the shell does, so the flag is read in every spelling and the command is denied. **None of the others is repaired, and the reason is the parser freeze of 2026-08-04**, recorded in the bullet below: the guarantee moved to the git hooks, each parser repair here has historically introduced its own defect, and widening a lexer to chase spellings is the coverage chase this project has twice removed checks over. The git hooks are unaffected by every one of them: what is lost is an early refusal in the session, not the boundary at the trunk. **And on a machine where jq or awk does not work, the deny says nothing at all:** the rule is simply absent there, and because the spellings it governs are exactly the ones that disarm the git hooks, the git hooks are no fallback for it.

</details>

<a id="parser-spellings"></a>
- **The session layer's one command reader is a frozen text parser, and a short list of spellings reads a command wrongly.** Since 2.8.0 the bypass deny's lexer is the only session code that reads command text (the scope hook reads file paths): it moved verbatim, it is frozen and pinned by digest (changed three times since, by decision: in 2.8.0 to stop the false denials its own review found, in 2.10.0 to stop two more and to read a heredoc piped into an interpreter, and in 2.11.0 to read a walked wrapper's options by its own grammar and to stop counting a reader that can run a shell as data), and a short list of spellings still misleads it.
  **What to do:** Read the bypass deny as a nudge and the git hooks' refusals as the answer; keep the `Architecture diagram:` label on one line of the spec, inside the Closing report, because that one item is read the same way by the git hooks.

<details><summary>The history and the measurements</summary>

**For all but one item the git hooks judge the same operation correctly afterwards.** The one exception is not a command and is recorded here because this bullet has always carried it: the architecture-diagram field is read from the whole spec rather than from the Closing report section, so a mention of the label ELSEWHERE in the spec can decide it in either direction (the readers take the FIRST matching line, ruled first-line-wins in 2.3.0), and that first-match reading is in the merge hook and the audit alike, so no later layer corrects it and it can let work reach the trunk. What the lexer misreads is measured: the spellings that defeat its one refusal are in the hard-deny bullet above. In the refusing direction the 2.8.0 adversarial review measured three classes on the shipped bytes, and the owner ruled them FIXED in 2.8.0 inside the pinned lexer, the one exception taken to the freeze: a heredoc body written through `cat`, `tee` or `git` that quotes a disarming spelling (in 2.8.0 for the spaced spelling, `cat << EOF`; since 2.10.0 also for the no-space spelling, `cat<<EOF`, and behind a prefix a person types before the command: an assignment, `env`, `export`, `command`, `nohup`, `exec`, `sudo` or one leading redirection), a read-only search whose pattern or post-`--` operand is the spelling (`git log -S --no-verify`, `git grep -- --no-verify`), and a combined short-flag commit whose message is the spelling (`git commit -am "--no-verify"`). One refusing case remains that blocks a command a person can actually run: a `git` word that is an argument to another command, such as `echo git commit --no-verify`, is still denied although it runs no git. A second was measured by this release's own fix round and left as it stands: a search that puts the spelling in OPTION position, such as `git grep -n --no-verify` or `git log -p --no-verify`, is still denied, and git itself refuses that spelling (`error: unknown option`), so what the deny turns away there is not a command that could have run. Every spelling git accepts as a search for the token is allowed, with or without other flags, and whether the search option stands alone or is combined with others: `git grep -e --no-verify`, `git grep -n -e --no-verify`, `git grep -- --no-verify`, `git grep -n -- --no-verify`, `git log -S --no-verify` and `git log -pS --no-verify`. (A commit message that is exactly an escape spelling, such as `git commit -m SETLIST_SKIP_HOOKS=1`, was denied until the 2.7.0 leg's fix and is not any more.) Everything else is FROZEN by decision: the lexer and its corpus are closed to new spellings as of 2026-08-04, because the guarantee moved to the git hooks and each parser repair has historically introduced its own defect, and since 2.8.0 its bytes are pinned by digest, so a widening is a visible decision rather than a drift. **Through 2.7.0 this bullet described three advisory gates and listed some twenty spellings the commit gate and the close gate misread**, from a checkout run in a different repository to a quoted merge operand outside the ASCII keep-class, two of them with bullets of their own (a `<<\EOF` heredoc read as code, and `@{u}` refused as unnameable). Every one was a property of those two parsers, and all of them left with the parsers in 2.8.0, the two bullets included; the bypass deny's own lexer read heredoc bodies as commands too, a separate refusal fixed in 2.8.0 and described above. **2.10.0 changed the lexer a second time, by decision, and names what it left.** Two false denials of ordinary work were fixed (a prefix before the heredoc's command, and the no-space operator, with an arithmetic shift such as `$((1<<2))` still never read as an operator), and one crafted bypass was closed: a heredoc piped into `bash`, `sh` or `zsh` later in the same pipeline (`cat << EOF | bash`, `cat << EOF | tee log | bash`) has its body judged as commands. What it left, each pinned in the suite in its observed direction: a prefix outside that list keeps the old denial (`sudo -u root cat << EOF`, `nice cat`, `time cat`, `env -i cat`), the conservative direction; an interpreter the re-judge does not name (`| dash`, or `| awk '{system($0)}'` behind a plain owner) is not re-judged; and four crafted spellings still carry a heredoc's body past the deny to an interpreter, each with a PLAIN owner (no prefix, no glued operator): an interpreter behind a wrapper spelled by its path (`| /usr/bin/env bash`), a heredoc inside a brace group whose output is piped on (`{ cat << EOF; } | bash`), a redirection such as `2>&1` before the pipe, and a pipe carried past the newline to a later line. **This release's own adversarial review closed three more and fixed two false denials**, each red first: a substitution around the opener is judged wherever it was opened, on the opener's line as on an earlier one (`eval $(cat << EOF ...)`); a walked wrapper's no-value options no longer eat the interpreter behind them (`| command -p bash`, `| exec -a x bash`); each body is credited to its own opener, so a body one segment reads as data is no longer judged because a later opener on the same line is piped to a shell; a backslash-newline continuation is joined rather than made into a word, which stopped refusing an ordinary `git commit -m \` across two lines and a read-only `git log --grep \`; and a new-owner heredoc piped to a data sink (`cat<<EOF | tee -a FILE`) is data, where the redirection spelling one character away already was. **2.11.0 changed it a third time, by decision**, for the 2.10.0 second leg's findings: a walked wrapper's options are read by that wrapper's own option grammar, the rules getopt applies, so a glued, bundled or long option, one the old list lacked, or a `NAME=value` word no longer hides the interpreter behind it (`| env -Sbash`, `| sudo -Hu root bash`, `| env --unset A bash`, `| env -C . bash`, `| env -i A=1 bash`); `nice` and `time` are walked the same way (`| nice bash`, `| time -p bash`); `sudo -s` or `sudo -i` with no command after it is read as the shell it starts; and `awk`, `sed`, `less` and `more` left the list of data sinks, because each has a command that runs a shell, so a new-owner heredoc piped to one is judged (`cat<<EOF | awk '{system($0)}'`). The git hooks refuse what any of them would commit, and the deny is a nudge, as the bullet above says. **The short form and this text used to disagree**, one saying all but one item and this one saying two, because the heredoc member had once run your gate command before an ordinary commit; that stopped in 2.6.0 and the member has left, so both layers now say one.

</details>

<a id="armed-check"></a>
- **The session layer's one deny stops a command that disarms the hooks for its own run; a persistent change to `core.hooksPath` or `merge.ff`, and a fresh clone, are reported at the next session start and refused by nothing.** `git config core.hooksPath /dev/null`, `git config --unset core.hooksPath` and a fresh clone, whose `.git/config` was never armed, leave the git hooks off for every later command; the deny does not read them, and at the next session start the re-grounding hook reports the setting, its value and the command that restores it on one line, `[SR-HOOKS-NOT-ARMED]`.
  **What to do:** Run `/setlist:upgrade` when a session opens with that line (from the main worktree, in a linked one); on a team, the forge check on a trunk that requires it is the layer a disarmed clone cannot switch off.

<details><summary>The history and the measurements</summary>

Found by the 2.9.0 external review; the report arrived in 2.10.0. It reads the repository's own configuration (`git config --local`, the file the stamp and the refresh write), so the environment forms of git's configuration (`GIT_CONFIG_COUNT`, `-c`) and a user's global setting are outside what it reads, and so is a hook file whose execute bit was removed (`chmod -x`), which is a mode rather than a setting. It is silent on an armed instance, before the repository exists, and outside an instance; where git cannot be asked at all (git missing, or a configuration it cannot read) it says THAT instead, `[SR-CONFIG-UNREADABLE]`, rather than reporting an armed clone as unarmed. On a machine where jq does not work the line names the setting without its value, because a value is text the instance controls and that path has no escaper. It is a report and not a refusal: SessionStart has no deny, and the deny's own reach is the hard-deny bullet above.

**The wiring check's spelling restriction, a bullet of its own through 2.10.0 ("The wiring check recognises only the command spellings `settings.json.tmpl` ships."), retired in 2.11.0.** `refresh-instance.sh` used to certify a hook entry as wired by matching its command against an enumerated set of spellings, which failed both ways: `bash "$CLAUDE_PROJECT_DIR"/.claude/hooks/bypass-deny.sh`, which runs the stamped file, was reported `NOT WIRED` and `--apply` exited 3, while `"$CLAUDE_PROJECT_DIR"/.claude/hooks/bypass-deny.sh >/dev/null`, which runs it and discards the decision it prints, was certified wired because its first word matched; and a comma-joined matcher (`Write,Edit,MultiEdit,NotebookEdit`), which the harness accepts, was reported `NOT WIRED` by the wiring predicate while the coverage predicate beside it accepted it. Since 2.11.0 an entry is wired when the file its command runs IS the stamped file (the same file on disk): the command must be one plain run of one file, optionally through `bash` or `sh`, named by an absolute path or through `$CLAUDE_PROJECT_DIR` (an unquoted 8.3 short path, such as `C:/PROGRA~1/...`, is not read as one plain word and reads `NOT WIRED`: a hand-written spelling no Setlist writer produces, so quote it or write the long form), and anything else (an argument, a redirect, another variable, a pipe, a subshell) reads `NOT WIRED` with the entry named; a comma-joined matcher is read as the alternation it means. The check reads the settings file; it does not run the hook, so what the wired file itself does is the hook's business, not the check's.

</details>

#### Teams: the forge, ownership and custody

<a id="forge-check-required"></a>
<a id="forge-protection-now"></a>
<a id="forge-own-copy"></a>
- **The forge check reads what the forge exposes: it governs the merge button only where the trunk requires it, reads the trunk's protection as it stands now, and runs the pull request's own copy of itself.** The stamped check (2.6.0) runs the close verification, the attestation walk, the content scan, the third gate tier and the trunk audit against the merge a pull request would make, and refuses on any of them; the forge's merge button then enforces what the local gate would have. Under `forge` custody it verifies that the trunk requires a review, review from Code Owners and this check NOW and that the flip is on the trunk; a trunk protected after an unreviewed flip landed verifies that flip. The workflow, the hooks and the check the job runs are the files in the pull request's checkout, so a pull request that edits them is judged by its own edit; the stamped CODEOWNERS names those paths, and the forge enforces an owner's review only under its "Require review from Code Owners" setting, which the check reads.
  **What to do:** Require the check, one approving review and review from Code Owners in a ruleset on the trunk, disable rebase merging there, and require branches to be up to date before merging. Protect the trunk before the first custody flip lands, fill the CODEOWNERS `@OWNER` slot, and read the check's enforcement-path line on a pull request as the cue for that review.

<details><summary>The history and the measurements</summary>

What it cannot do is require itself: a trunk that does not list it as a required check has a report, not a boundary, and under `forge` custody the check refuses for exactly that reason. It does not review merge diffs (the bullet below stands). A repository that merges by REBASE lands every branch commit on the trunk as direct feature code: the check reports the setting before the fact, no later run of the check sees the commit (each run audits only its own range), and an armed clone's `pre-push` refuses every push of that trunk from then on, so disable rebase merging on a trunk the check governs. And the check judges the merge against the base its checkout carries: the forge's own setting that requires a branch to be up to date before merging is what keeps that base current; the check reads it and, under `forge` custody, refuses a trunk that requires the check without it (`FC-STRICT-NOT-REQUIRED`, since 2.7.0; this sentence said the check did not read it until 2.10.0), and it is still a setting you turn on, which the check cannot turn on for you.

**Until 2.11.0 this bullet was titled "The forge check governs the merge button only where the trunk requires it.", and two bullets of their own stood beside it, merged here in 2.11.0** because all three are one fact about the forge check, that it can judge only what the forge exposes when it runs: "The forge check reads the trunk's protection as it stands, not as it stood." and "The forge check runs the pull request's own copy of itself, and what makes an edit to it a reviewed change is the forge's code-owner review setting, which the check now reads.".

**The protection as it stands.** The stamped CODEOWNERS makes the paths that matter reviewed changes where the trunk requires review from Code Owners, which the check reads (2.10.0); the forge's audit log is where the rest of that history lives, and the check does not read it.

**The pull request's own copy.** Found by the 2.9.0 external review, and closed in 2.10.0 as far as a check can close it. Under `forge` custody the check reads the setting from the trunk's protection and refuses when it is off (`FC-NO-CODE-OWNER-REVIEW`); under every other custody it reports it beside the review count. When a pull request's diff touches `.githooks/`, `.claude/hooks/` or `.github/workflows/`, the check reports so by name under every custody (`FC-ENFORCEMENT-PATH-TOUCHED`), before any step can refuse; a report and never a refusal, because the reviewed change is the mitigation. Running the base branch's copy instead was considered and declined: on a `pull_request` event the workflow definition itself is the pull request's, so a base-branch script run by a workflow the pull request controls moves the question one file up without answering it, and two copies of one mechanism is the shape the check's own header refuses.

</details>

<a id="codeowners-bridge"></a>
- **The CODEOWNERS bridge reads a subset of the file's grammar, and a pattern is a claim about paths.** The audit and the forge check evaluate `Owns:` declarations against the repository's CODEOWNERS file (the core grammar the forges share: patterns, `@login`, `@org/team`, emails, last match wins) and refuse a close that declares a file another owner's pattern claims.
  **What to do:** Write CODEOWNERS in the core grammar (patterns, `@login`, `@org/team`, emails) and let the forge resolve handles.

<details><summary>The history and the measurements</summary>

Sections, negations and character classes are refused by name rather than guessed at. **Why character classes stay refused (2.11.0, spec 0173):** GitHub's own CODEOWNERS grammar evaluates no character class (its documentation says a `[ ]` range "doesn't work", and that a line with invalid syntax is skipped), and the forge check reads `Owns:` with this same reader, so a reader here that evaluated `[ab]` as a class would claim files for an owner the forge itself does not, a refusal of a close the forge accepts. Refusing the line by name keeps the two readings one. Whether GitHub skips such a line or matches it literally is measured at the release gate where a scratch repository is available. Locally, only email owners can be matched; a handle or a team is resolved at the forge, and the audit reports rather than refuses when it cannot resolve one. Ownership here is what the file says, not what an organisation chart says.

</details>

<a id="declarations-claim"></a>
<a id="custody-key"></a>
- **A declaration is a claim, not a verified fact: the single-parent close arm is as strong as your `Owns:` lines, and the integrity chain as strong as where your signing key lives.** A spec declares the files it owns (`Owns:` lines in its header); a single-parent close is audited file by file against that declaration, so a close can no longer exempt a whole commit by flipping one status row. An attestation binds an approval to a spec's exact bytes and the git hooks refuse a build commit whose spec has drifted since that approval, and a key your build can reach is not custody.
  **What to do:** Declare ownership in every spec, put a custody behind the declaration, and read `/setlist:validate` when the page and the record disagree. Declare the custody you actually have; if a boundary against deliberate evasion is the need, it is the forge check required on your trunk.

<details><summary>The history and the measurements</summary>

But the declaration travels in the same commit it justifies: whoever writes the close can write the declaration, and the hooks verify coverage, not truth. With a declared attestation custody the declaration sits inside the approved, signed spec bytes, so changing it costs a human re-approval; without one, it is an explicit line in your history that review and `/setlist:validate` can catch, and nothing more. **A spec that declares nothing closes under the pre-2.4.0 rules**, the whole-commit exemption included, so the audit is only as complete as your adoption; chores declare their files in the machine record (`chores.<id>.files`), which no attestation covers, so the chore route is the weaker one by exactly that much. And the machine record in `.claude/status.json` is what the hooks read: the human STATUS.md page is for people, and a hand-edit can make the page disagree with the record until `/setlist:validate` reports it.

**Two specs in flight that declare one file (2.11.0):** at a two-parent close the audit reads the trunk's own first-parent commits since the branch left the trunk, and refuses the close by name (`SLH-OWNS-OVERLAP`) when a spec one of them closed declares a file this close declares; the remedy is to merge the trunk into the spec branch and close again. It reads no other branch, so three shapes are its boundary: a second close landed by squash or fast-forward has no branch point and is not compared; the `git pull` sync shape (a clone that closed on a stale trunk and pulled) puts the earlier close on the pull merge's second parent, off the line the audit reads, and passes; and a branch that took the earlier spec by merging that spec's BRANCH rather than the trunk is refused although it carries the change, a false refusal the same remedy clears. A close whose own `.claude/sdd.json` stamps a plugin older than 2.11.0 is not asked the question, so an upgrade never condemns parallel closes made before it.

**Until 2.11.0 this bullet was titled "The close audit's single-parent arm is as strong as your declarations, and a declaration is a claim, not a verified fact.", and the signing key was a bullet of its own, "The headless integrity chain is only as strong as where your signing key lives, and a key your build can reach is not custody.", merged here in 2.11.0** because both say one thing: what the hooks verify is that a declaration is present and signed, never that it is true. Its history follows.

It does not stop the unapproved build from HAPPENING: the only layer present when code is written is the session layer, and that layer has been advisory in mechanism since 2026-08-04. It stops the result becoming a commit, and at push, being shared. **A signature proves a key was used, not that a person decided.** If the signing key sits where the build process can read it, a headless run can sign its own approval and the chain will verify: what it then proves is that the run had the key, which is not the question. Setlist therefore makes you DECLARE your custody, and prints that declaration in every verification it emits, including the ones that pass, so the strength of the claim travels with the claim. Two things it does not close under `signer` custody, named rather than implied: **the allowed-signers file is read from the tree under review**, so a committer who can push a key enrolment and a signed attestation in one range verifies under that key (a forge that protects `.claude/` through the stamped CODEOWNERS makes the enrolment a reviewed change, which is the mitigation and not a fix); and **`--no-verify` and an unset `core.hooksPath` bypass this exactly as they bypass every other git hook.** Under `forge` custody (built in 2.6.0) there is no key: the approval is the ACTIVE flip landing on the protected trunk through a required review, verified by the stamped forge check, and what that establishes is that the forge's review happened, with the forge's account security as the custody. If you need a boundary that holds against deliberate evasion, it is that check, required on your trunk.

</details>

<a id="hashed-range-cut"></a>
- **The hashed range ends at the FIRST line reading `## Closing report`, fences included, and the ownership reader agrees with that cut.** The range a spec's hash signs is cut by the first line matching the Closing-report heading read RAW, so a fenced or quoted copy of the spec template ABOVE your `Owns:` declarations ends the range early, and a declaration below that quote is refused as out-of-range even though it sits above your real Closing report.
  **What to do:** Keep declarations above any quoted `## Closing report` line, or drop the quoted heading.

<details><summary>The history and the measurements</summary>

This is a decided boundary, not an accident (2.4.0 review, ruled 2026-09-01): the ownership reader and the hash cut are kept byte-agreed, because a declaration the reader accepts but the signature does not cover would put the ownership set outside what a human approved, silently, exactly where this layout occurs. The refusal names the cause and the one-edit fix: move the declarations above the quote, or drop the quoted heading line. The suite pins the agreement, so a future fence-aware reader has to move the hash cut, the custody question and this bullet in one commit.

</details>

<a id="stop-hook"></a>
- **A session killed from outside fires no Stop, and the Stop hook is a nudge, never a lock.** The stamped Stop hook (2.6.0) refuses to end a turn that leaves a spec or `specs/STATUS.md` change unstaged, once per turn, and allows the continuation the harness marks, so a change the session cannot stage costs one refusal and never a hang.
  **What to do:** Stage the spec and the page before ending a turn; do not read the Stop hook as enforcement.

<details><summary>The history and the measurements</summary>

A session killed from outside, or one that never reaches its Stop event, fires nothing, and a change staged and never committed is not its question; the git hooks are what refuse the work. Its reason is delivered to the agent, as the bypass deny's is and, since 2.9.0, the scope hook's through `additionalContext` (Design boundaries above).

It is silent where the project root has no `.git` entry of any type, which is the state `/setlist:new` leaves until `/scaffold` creates the repository; 2.6.0 to 2.8.0 refused there, at the end of every new project's first session. The same silence covers an instance stamped below an enclosing repository's top, whose git layer the stamp already reports as not armed, so a spec left unstaged there ends the turn unrefused. A linked worktree (a `.git` file), a corrupt `.git` and a dangling `.git` symlink are still refused. Until 2.10.0 there was one exception, measured by the 2.9.0 adversarial review and standing since 2.6.0: a corrupt `.git` beneath an enclosing repository was not refused, because git walked past it and read the enclosing repository in its place. Since 2.10.0 the hook compares git's top-level with the project root, physically, and refuses by name (`SP-NO-GIT`) when they differ while a `.git` entry exists at the root.

</details>

#### Deliberate evasion

<a id="crafted-merges"></a>
<a id="sideways-routes"></a>
<a id="evil-merge-edit"></a>
- **Deliberate evasion: a committer who crafts history to pass the trunk audit can, and the list of known routes is maintained rather than complete.** The audit reads history and judges each merged parent; it does not attribute individual files to the spec that authorised a merge, because that is not decidable from history. The known routes, each measured:
  - **Crafted merges.** A chained merge (unspecced code merged INTO a spec branch, then that branch closed compliantly) and its octopus spelling INTO a spec branch reach the trunk behind a compliant close; an octopus ONTO the trunk is refused by name since 2.11.0 (`SLH-OCTOPUS-MERGE`).
  - **Sideways routes to the trunk.** Content can reach the trunk without a closing merge the merge hook reads, by five commands a person runs for ordinary reasons: `git cherry-pick` of spec-branch commits (git fires no hook for it), a merge performed on a detached HEAD (no current branch, so no hook sees a trunk target), `git rebase` onto a spec branch and `git reset --hard <spec-branch>` (no merge commit, so no merge hook runs), and the pathspec `git checkout <spec-branch> -- <path>` (the commit that follows is ordinary, and `pre-commit` scans content rather than provenance). For cooperating use the trunk audit refuses each at push and the remote is untouched, with one qualification: composed with a compliant single-parent spec close that declares no ownership, the audit's close exemption applies and the push succeeds, while a close that declares is audited file by file.
  - **A merge that edits a file outside its conflicts.** It reports role-path files a merge commit introduced that no parent carries, which covers `git commit --amend` on a completed merge and evil merges that ADD content; since 2.11.0, on git 2.38 and later, it also compares each two-parent merge with the clean merge of its parents and names every file that differs outside the files that conflicted (`SLH-MERGE-EDIT-OUTSIDE-CONFLICT`), reported rather than refused, and skipped by name on an older git.
  **What to do:** Put branch protection and required checks on your forge if evasion by a committer is in your threat model. Close specs with `--no-ff` through `/setlist:checkpoint`, take a file from a spec branch through the spec that owns it, use `git reset --hard` on a trunk only to discard local commits, declare ownership so the audit reads a close file by file, and review the files a merge's conflicts touched, reading the audit's report of any edit outside them.

<details><summary>The history and the measurements</summary>

**Until 2.11.0 this bullet was titled "Merges crafted to evade the trunk audit can succeed, and the list of known routes is maintained rather than complete.", and two bullets of their own stood under this group beside it, merged here as its routes in 2.11.0** because all three are one boundary, a committer arranging history the audit judges: "Sideways routes to the trunk." and "The trunk audit reports a merge that edits a file outside its conflicts, and cannot tell an edit inside them from conflict resolution.".

**Crafted merges.** Two routes are known and OPEN: a chained merge (unspecced code merged INTO a spec branch, then that branch merged with a compliant close), and the OCTOPUS spelling of the same trick, where parent order hides the unspecced parent behind a catch-up parent. Both were found by adversarial review rather than by use. Both were refused for a while, and the checks that refused them were removed on 2026-08-07, because neither could tell the crafted shape apart from ordinary work: the chained-merge check reported `git pull` on a shared trunk as a violation, naming as the offender the compliant close merge it had passed clean minutes before. That is the second developer on any team, on the commonest git command there is. A false denial on ordinary work costs more here than the bypass it prevents, so the route is documented instead of defended. The history is the point of this bullet: the second route was introduced by the fix for the first, and the fix for both broke everyday use. A cooperating developer does not construct these; someone determined to bypass the audit will find the next one before we do. Put branch protection and required checks on your forge if that matters to you.

**Since 2.11.0 an octopus ONTO the trunk is refused by name** (`SLH-OCTOPUS-MERGE`), at merge by `pre-merge-commit` and `pre-commit` and at push by the audit for any such merge made after the instance adopted the rules, when the merge's own tree stamps plugin 2.11.0 or later (an octopus an earlier release accepted is not refused after an upgrade): a close merges one spec branch, so a merge of several branches onto the trunk at once is never a compliant close, and the shape needs no discriminator. It is not the octopus route above, which merges INTO a spec branch and reaches the trunk through an ordinary two-parent close; that route, and the chained one, stand as written.

**Sideways routes.** Merging a spec branch under a second NAME used to be on this list and left it in 1.0.8, when the close gate began resolving a merge argument to a COMMIT; since 2.8.0 the git hooks judge a merge by the spec rows it closes, which makes the name irrelevant (the alias paragraph below). The remaining routes are named rather than parsed, and a visible edge is more honest than a half-parser that would miss the next spelling. Each of them is caught by the trunk audit below FOR COOPERATING USE, which is why the layers exist: the per-merge hooks refuse at the moment of a merge they can see, and the audit reads history afterwards so it does not care how work arrived. It is not immune to being spelled around either: merge TOPOLOGY crafted to evade it (a chained merge, an octopus parent order) is a separate class, the first route above, and closing those routes has not been convergent. `git pull <remote> spec/...` used to be on this list as a fetch-and-merge the close gate did not intercept; its merge runs `pre-merge-commit`, which refuses unclosed work with `SLH-CLOSES-NO-SPEC`, measured for 2.8.0.

**Three routes were bullets of their own from 2.6.0 to 2.9.0, merged here in 2.10.0**, split out then because each is a command a person runs for ordinary reasons while the close gate was an early layer that missed them; since 2.8.0 there is no early layer to miss them, and all three ended in this bullet's sentence. Each was measured on the shipped bytes with controls in both directions (a compliant close pushes clean, an unclosed merge on the trunk is refused). **`git rebase` onto a spec branch** ("brings that branch's commits to the trunk with no closing merge"): Measured: run on the trunk, it leaves the spec's role-path file on the trunk, and the next `git push` is refused with `VIOLATION ... feature code committed directly to main`, remote unchanged. Through 2.7.0 the suite pinned this route through the close gate; since 2.8.0 no case drives it end to end, and the suite's ledger says so rather than claiming a pin. Close a spec with `--no-ff` instead, which is what `/setlist:checkpoint` does. **One qualification, measured by adversarial review and corrected here:** that refusal holds for the bare form. Composed with a compliant single-parent spec close that declares no ownership, the audit's close exemption applies and the push SUCCEEDS; a close that DOES declare is audited file by file instead. See the single-parent declarations bullet above for the exemption and its limits. **`git reset --hard <spec-branch>`** ("moves the trunk onto unclosed work outright"): Measured: the trunk ends up at the spec branch's tip carrying its role-path file, and the push is refused with the same `VIOLATION`, remote unchanged. Reach for `git reset --hard` on a trunk only when you mean to discard local commits, never as a way to take a branch's work. **One qualification, measured by adversarial review and corrected here:** that refusal holds for the bare form. Composed with a compliant single-parent spec close that declares no ownership, the audit's close exemption applies and the push SUCCEEDS; a close that DOES declare is audited file by file instead. See the single-parent declarations bullet above for the exemption and its limits. **The pathspec `git checkout <spec-branch> -- <path>`** ("copies role-path files onto the trunk without any merge to read"): Measured: the file lands on the trunk at exit 0 and the push is then refused with the same `VIOLATION`, remote unchanged. If you want one file from a spec branch, take it through the spec that owns it. **One qualification, measured by adversarial review and corrected here:** that refusal holds for the bare form. Composed with a compliant single-parent spec close that declares no ownership, the audit's close exemption applies and the push SUCCEEDS; a close that DOES declare is audited file by file instead. See the single-parent declarations bullet above for the exemption and its limits.

**An alias of a spec branch was also a bullet of its own until 2.10.0** ("An alias of a spec branch is judged by what its merge closes, never by the name it was merged under."), and it left the list because it describes the mechanism working rather than a place it stops: the git hooks never identified a close by its branch name, so an alias of unclosed work is refused whatever it is named. Measured for 2.8.0 on an instance armed with the stamped hooks: an alias cut at an unclosed spec branch, merged onto the trunk after the spec branch advanced, is refused by `pre-merge-commit` with `SLH-CLOSES-NO-SPEC` and the trunk does not move; the suite pins that case. Through 2.7.0 both guarantee layers were verified by execution to refuse the same merge while the session layer's warning disappeared, and this bullet recorded that residue; the residue left with the gate. **A decided boundary rather than an open defect, moved to this group 2026-09-02**: a close is what a merge flips, not what a branch is called.

**A merge that edits outside its conflicts.** An edit INSIDE a file that conflicted is indistinguishable by content from a legitimate conflict resolution, so it is not flagged: flagging it would refuse every real merge. **Until 2.11.0 the title read "The trunk audit cannot tell a merge that EDITS a file from ordinary conflict resolution."**, and this history said that a merge editing a file a parent already had "is indistinguishable by content from a legitimate conflict resolution, so it is not flagged: doing so would refuse every real merge". That held for every edit then; since 2.11.0 it holds only inside the conflicted set, because `git merge-tree --write-tree` computes the merge git would have made, and a resolution changes only the files that conflicted. The report is dated by the release: a merge whose own `.claude/sdd.json` stamps a plugin older than 2.11.0 is not compared, so an upgrade never reports on history made under older rules. It reports rather than refuses for this release, measured across one before a refusal is considered; a merge made with a strategy that keeps one side whole (`-s ours`) is reported too, because its tree differs from the clean merge outside any conflict.

</details>

<a id="bash-escape"></a>
- **The Bash escape hatch.** The scope hook watches the file-writing tools (Write, Edit, MultiEdit, NotebookEdit), so a session that writes files through Bash instead (`cat >`, `sed -i`, a heredoc) does not trip it, and `pre-commit` checks what a commit contains rather than which tool wrote the file.
  **What to do:** Read the deny list as a spelling list (the conventional secret-bearing `.env` names and `Bash(cat .env*)`) and the audit as the backstop.

<details><summary>The history and the measurements</summary>

The same boundary applies to git itself: the bypass deny reads the command it is given, so a git command run through another interpreter (`sh -c '...'`, a backtick, a script file) is not a command it can read; a heredoc piped into `bash`, `sh` or `zsh` is read since 2.10.0, with the crafted spellings the parser bullet names. Wrapper prefixes that a person actually types (`command`, `env`, `nice`, `nohup`, `exec`, and leading `VAR=value` assignments) are handled by its lexer for `--no-verify` and `-c core.hooksPath`, but NOT for the escape variable, which it reads only at assignment position after nothing but a bare `env` or `export` (the hard-deny bullet names the measured spellings); and that list is not a claim of completeness and cannot be one. The trunk audit below is the designed catch for this whole family: it reads what ended up in your history and does not care how the command was spelled. The stamped deny list is the same kind of thing and its template says so in a `_comment` key: the Read rules stop the Read tool on seven conventional secret-bearing names (`.env`, `.env.local`, `.env.*.local`, `.env.production`, `.env.development`, `.env.staging`, `.env.test`; narrowed in 2.10.0 from `Read(.env.*)`, which also hid the `.env.example` the stamp writes), and, since 2.6.0, `Bash(cat .env*)` stops one Bash spelling; a secret file named any other way is not covered.

</details>

<a id="advisory-persuades"></a>
- **The scope hook's warning reaches the agent, and the agent may proceed anyway: advisories persuade, hooks refuse.** Since 2.9.0 the scope hook carries its reason in `additionalContext`, which Claude Code adds to the agent's context beside the tool result, and the agent reads it before the write lands. Since 2.11.0 the hook answers no permission prompt: it prints no permission decision, so Claude Code asks you about the write as your permission mode decides, and the warning reaches the agent all the same. A delivered warning is not a refusal: an agent may attribute the text to the hook, judge the write harmless, and proceed, and the git hooks are what refuse the work at commit, merge and push.
  **What to do:** Read the scope hook's warning as advice the agent has seen; rely on the git hooks' refusals, not on the agent heeding it.

<details><summary>The history and the measurements</summary>

**Until 2.9.0 this was an Upstream condition, "The scope hook's warnings do not reach the agent on current harnesses."** The hook emitted its reason on `permissionDecisionReason`, `systemMessage` and a machine-readable `setlistAdvisory` field, and none of them reached the model when the hook's decision permitted the write, which an advisory's decision then always did. That bullet's own history recorded the plan: if a probe confirmed the sibling field `additionalContext` delivers an advisory to the model, the bullet would become an open limitation whose fix is to use that field. **It skipped that step:** the confirmation and the fix landed in the same release, so the open state never stood on a published list, and the bullet was replaced by this boundary rather than moved.

**How 2.9.0 measured it, at Claude Code 2.1.274.** Two arms, each a scratch instance whose minimal hook emits `additionalContext` carrying a per-run sentinel and an instruction to emit a token, and writes a marker when it fires: one on PreToolUse beside a decision that permitted the write, one on PostToolUse. Each was read against a negative twin (the 2.8.0 scope hook wired on the same event, with a marker hook beside it) in the same run, and a control proved a hook's deny reason reaches the session and the deny takes effect. Both arms read SEEN (marker fired, sentinel echoed, token emitted), both twins NOT-SEEN with their markers fired. The scope hook uses PreToolUse, so the warning arrives before the write.

**What the old channels actually did.** In that run the 2.8.0 hook's reason reached the session transcript exactly once, as a system informational notice addressed to the user (`PreToolUse:Write says: setlist [SH-TRUNK-WRITE] ...`), and never in the model's own text: routed to the user's channel, not dropped. That notice carries the `setlist ` prefix only `systemMessage` carried. 2.9.0 removed `systemMessage` and kept `permissionDecisionReason`, which the vendor documents as shown to the user beside a decision that permits; 2.11.0 removes it with the decision itself.

**How the NOT-SEEN lines of 2.6.0 to 2.8.0 were taken.** The per-release probe of those releases had no marker to prove its hook fired, and its session wrote `src/App.js` into a scratch instance already holding `src/app.js`; on a case-insensitive filesystem that is one file, and the write tool refuses such a write before any PreToolUse hook runs. Those lines therefore could not tell a dropped reason from a hook never dispatched. The 2.9.0 twin measured the drop on a hook proven to have fired.

**Why it persuades rather than refuses.** An agent has been measured attributing an injected advisory correctly to the hook rather than the user, then proceeding on its own judgement that the action was harmless. That is the delivered channel working as designed, and it is why the scope hook stays advisory: the refusal is the git hooks' job.

**The scope hook's path matching, enumerated in 2.9.0 and fixed in 2.10.0.** Found in 2.9.0 by enumerating the scope hook's path predicate case by case before its warning began reaching the agent, because a wrong verdict the agent can read is louder than one it cannot. Nine cases: case variance of a role path, a symlinked leaf, a symlinked role directory, a path git would quote, a non-ASCII name, dot segments, a trailing slash on the recorded role, this one, and a docs path beginning with a role's letters (which must stay silent). Three missed, and each was a bullet through 2.9.0: a role directory spelled in a different case on a case-insensitive filesystem ("A role directory spelled in a different case is not seen by the session scope gate on macOS or Windows."), a symlinked leaf, which that bullet also carried, and a relative write path read against the project root ("A relative write path is read against the project root, so the scope hook can miss a role-path write made from a subdirectory."). Each is pinned in the framework's own suite in its observed direction, so a change to the predicate turns the suite red and this bullet moves with it. Changing the predicate is a separate decision from disclosing it. Since 2.10.0 a relative path resolves against the working directory the tool call carries (the project root only when it carries none), a symlinked leaf resolves as its directory already did, for chains up to sixteen links, beyond which the hook reports that it stopped following rather than judging what it had reached (`SH-LINK-CAP`, advisory like the rest of this gate), and a role spelled in another case matches where a probe at run time finds the filesystem case-insensitive (a probe that cannot write leaves the match case-exact); the nine cases stay pinned in their new directions. Measured at Claude Code 2.1.276 and 2.1.280: a write through a symbolic link reaches this hook at the path the session wrote, not the path it resolves to, so the hook's own resolution stays the reading; through a link to a FILE the Write and Edit tools themselves then refuse the write and name the link's target, and through a symlinked DIRECTORY component they write (Edit, measured at 2.1.285), which the hook's resolution of the directory reads. **The trunk audit asks the same question at push, and until this release's adversarial review it asked it of the wrong filesystem**: its probe was written under the temporary directory, so a repository whose disk disagreed with that directory was judged by a filesystem nobody was auditing, in both directions, and a probe that could not run left the answer unset and reported clean. It probes the role directory's own volume now, not the temporary directory's, and a probe that cannot run refuses by name. One residue is folded at neither layer: a non-ASCII capital in a role directory's name, written in another case, is matched case-exact by the scope hook and by the audit alike, because both fold ASCII only.

### Upstream conditions (1)

Neither decisions nor defects in this project: conditions in software it depends on. Each names what would lift it and the check that re-measures it per release, so it stops being true by measurement rather than by anyone remembering to look.

<a id="hook-timeout"></a>
- **A timed-out hook is a skipped gate.** Claude Code cancels a hook that exceeds its timeout and lets the tool call proceed; that behavior belongs to the harness, not to the hook.
  **What to do:** Raise `timeout` in `.claude/settings.json` before the ceiling finds you, and fix PATH inside the gate command rather than in a profile.

<details><summary>The history and the measurements</summary>

The stamped settings therefore set explicit timeouts (300 seconds for each Bash hook since 2.6.0; through 2.5.0 the close gate carried 30 minutes because it re-ran your full suite inside the hook, a run 2.6.0 removed: the git hook runs the suite once, at the merge). If a hook outgrows its timeout, raise the `timeout` in `.claude/settings.json` rather than letting the ceiling find you. Relatedly, hooks run in a non-interactive shell: version managers wired into your interactive profile (nvm, pyenv, asdf) may be off PATH there, which shows up as a gate command that fails in the hook while passing in your terminal. That is a false deny, not a false pass; fix the PATH in the gate command itself. The harness also moves a hook's output longer than 10,000 characters to a file and shows the agent a 2,000-character preview; measured inside a stamped instance since 2.11.0, the scope hook's longest output is 1,742 characters (a recorded trunk of any length is now cut at 80) and the Stop hook's 951, so neither comes near it.
